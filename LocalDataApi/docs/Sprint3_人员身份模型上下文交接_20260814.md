## User 表当前迁移模式

`dbo.用户管理` **仍是 DB-First 混合迁移模式**：

- `User` 没有加入 `AppDbContext.typesManagedByMigrations` 白名单。
- `User` 仍会被 `ExcludeFromMigrations()` 排除。
- 因此 Task03-01 与 Task03-03 的迁移是先由 EF 生成快照，再手工补充 `AddColumn` / `AlterColumn` / `CreateIndex`。
- `Employee` 已由 EF Core 正常迁移管理。

## 重要风险（下一任务必须处理）

`IdentityId` 已是 `NOT NULL + UNIQUE`，但现有新用户创建路径尚未为其赋值：

- `Application/Identity/UserService.cs` 的密码注册和企业微信自动建号路径会新建 `User`，但未设置 IdentityId。
- `Application/Identity/RbacSeeder.cs` 的管理员种子用户也未设置 IdentityId。
- C# `long` 默认值为 `0`；首次新增用户可能写入 0，之后会因唯一索引导致失败。

建议优先创建 `dbo.UserIdentityIdSequence`，为 `IdentityId` 配置数据库默认值 `NEXT VALUE FOR dbo.UserIdentityIdSequence`，并在 EF 映射中使用 `HasDefaultValueSql(...)`。

## User 表 EF Core 直接管理建议

6. 后续 User 的字段、索引、约束统一由 EF Core migration 自动生成。

## User 表优化与删列建议

### 不能立即删除

- `PasswordHash`、`PasswordSalt`：密码登录正在使用。
- `WeChatWorkUserId`：企业微信登录使用，且已有唯一索引。
- `Role`：与 RBAC 的 `UserRole` 重叠，但种子、用户创建与登录响应仍在读写；应先完成 Role -> UserRole 的兼容迁移。
- `PrimaryDepartmentId`、`PrimaryDepartmentName`、`Position`、`IsLeader`：与 Employee 组织信息重复，但现有用户详情/列表 API 仍依赖。
- `IsActive`、`LoginFailCount`、`LockoutEnd`、`LastLoginTime`、`LastLoginIp`、`CreateDate`、`ModifyDate`：当前认证代码仍使用；其中多项是字符串，应后续渐进迁移为正确类型。

在删除前仍必须检查：存储过程、触发器、视图、报表、ERP 同步任务、前端和外部系统。

### 推荐的数据类型优化

| 当前列 | 建议目标 |
|---|---|
| `IsActive` 字符串 | `bool Enabled` |
| `LoginFailCount` 字符串 | `int FailedLoginCount` |
| `LockoutEnd` 字符串 | `datetimeoffset? LockoutEndUtc` |
| `LastLoginTime` 字符串 | `datetimeoffset? LastLoginAtUtc` |
| `CreateDate` / `ModifyDate` 字符串 | `datetimeoffset CreatedAtUtc` / `UpdatedAtUtc` |

| 部门/岗位缓存字段 | 通过 Employee、Department、Position 查询或建立明确同步策略 |

这些均应采用“新增 typed 字段 -> 回填 -> 双写 / 切读 -> 删除旧字段”的多阶段迁移，不能一次性 Alter 旧列。
