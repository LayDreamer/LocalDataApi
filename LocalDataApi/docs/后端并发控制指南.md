# LocalDataApi 并发控制实践（基于项目实际用法）

> 本文只整理 **`LocalDataApi` 当前代码里实际用到**的并发处理方法与逻辑，按「项目里怎么做的」来组织，而不是泛泛讲理论。每节给出：用到哪、逻辑是什么、代码位置、注意事项。
>
> 技术栈：.NET + EF Core（`AppDbContext`）+ SQL Server（遗留 ERP 库，中文表/列）。所有引用来自对当前代码库的只读调研，未改动任何源码。

---

## 1. 项目并发控制总览

本项目把并发控制做成**四道防线**，从外到内依次是：

```
HTTP 请求
  │
  ├─ ① 入口限流  [EnableRateLimiting("DatabaseHeavy")]
  │     并发闸门 64，排队 256，超额返回 429 + Retry-After
  │
  ├─ ② 单例资源保护  企业微信 Token 用 SemaphoreSlim 双检锁
  │     无锁快路径 + 锁内二次检查 + 提前 5 分钟失效
  │
  ├─ ③ 行级读写控制
  │     ├─ 乐观并发：8 个实体带 RowVersion，更新带客户端版本 → 冲突 409
  │     └─ 悲观取号：事务内 sp_getapplock 串行化「读 max+1」
  │
  └─ ④ 数据库护栏  唯一索引/约束 + rowversion 列（SQL Server）
        所有并发写冲突经 GlobalExceptionMiddleware 统一收口为 409
```

一句话：**用限流挡过载，用乐观并发 + 唯一索引兜大部分冲突，用悲观锁专门保护取号，用单例双检锁保护全局 token；冲突发生后统一返回 409 让客户端 reload，服务端不做自动重试。**

## 2. 入口限流：并发闸门 `DatabaseHeavy`

**用到哪**：`Program.cs` 注册；6 个 PMC 控制器统一标注 `[EnableRateLimiting("DatabaseHeavy")]`（如 `PMCBomController.cs:15`）。

**逻辑**：在请求进入业务前设并发闸门——同时放行的请求数上限 `PermitLimit`、超出部分进入队列 `QueueLimit`、队列也满则直接拒绝（429）。本项目用「并发数限制」而非速率限制，最贴合「保护数据库连接池」的诉求。

**代码**（`Program.cs`）：

```csharp
var databaseConcurrency = builder.Configuration.GetValue("Performance:DatabaseConcurrency", 64);
var databaseQueue       = builder.Configuration.GetValue("Performance:DatabaseQueue", 256);
options.AddConcurrencyLimiter("DatabaseHeavy", limiter =>
{
    limiter.PermitLimit          = databaseConcurrency;  // 同时放行 64
    limiter.QueueLimit           = databaseQueue;        // 再多 256 排队
    limiter.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
});
// 拒绝时返回 429 + Retry-After: 1
```

**注意**：
- 中间件顺序：`UseRouting → GlobalExceptionMiddleware → UseRateLimiter → UseAuthorization`。
- 与 `AddDbContextPool(poolSize: 256)` 是协调设计：64 并发重请求 + 256 排队，连接池 256 个连接复用，避免「拿到线程却拿不到连接」空转。
- `AddDbContextPool` 语义仍是 **Scoped**（每请求一个 `AppDbContext`），实例来自复用池，**`AppDbContext` 仍非线程安全**（见 §9）。

## 3. 单例资源的进程内并发：企业微信 Token 双检锁

**用到哪**：`Infrastructure/WeChatWork/WechatWorkTokenProvider.cs`（注册为单例）。企业微信 `access_token` 是企业级全局配额，新 token 会让旧 token 失效，必须进程内共享一份，不能每请求刷新。

**逻辑（异步双检锁）**：先用「无锁快路径」判断缓存是否有效（绝大多数请求命中，零竞争），无效才进入 `SemaphoreSlim(1,1)` 临界区；进锁后再**二次检查**（排队期间可能已被别的请求刷新完），避免「惊群」重复刷新。

```csharp
private readonly SemaphoreSlim _tokenLock  = new(1, 1);  // 保护 AccessToken 刷新
private readonly SemaphoreSlim _ticketLock = new(1, 1);  // 保护 JsApiTicket 刷新

public async Task<string> GetAccessTokenAsync(CancellationToken ct = default)
{
    if (_accessToken != null && _tokenExpireTime.HasValue
        && DateTimeOffset.UtcNow < _tokenExpireTime.Value)        // ① 无锁快路径
        return _accessToken;

    await _tokenLock.WaitAsync(ct);                              // ② 异步互斥
    try
    {
        if (_accessToken != null && _tokenExpireTime.HasValue
            && DateTimeOffset.UtcNow < _tokenExpireTime.Value)    // ③ 二次检查
            return _accessToken;

        var response = await _client.ExecuteCgibinGetTokenAsync(new CgibinGetTokenRequest(), ct);
        if (response.IsSuccessful())
        {
            _accessToken = response.AccessToken;
            _tokenExpireTime = DateTimeOffset.UtcNow
                .AddSeconds(response.ExpiresIn).AddMinutes(-5);   // ④ 提前 5 分钟失效
            return _accessToken;
        }
        throw new InvalidOperationException($"获取 AccessToken 失败: [{response.ErrorCode}] {response.ErrorMessage}");
    }
    finally { _tokenLock.Release(); }                            // ⑤ finally 释放，异常不死锁
}
```

**为什么这样写（本项目取舍）**：
- 用 `SemaphoreSlim` 而非 `lock`：临界区跨 `await`（HTTP 调用），`lock` 不允许 `await`。
- `try/finally + Release()`：异常与取消路径都不泄漏许可（不死锁）。
- 提前 5 分钟失效：预留时钟偏移与网络抖动的安全边界。
- 内部只用 `IHttpClientFactory` 命名客户端，单例内绝不持有裸 `HttpClient`（避免 socket 耗尽 / DNS 陈旧）。

**注意（非阻塞）**：
- 嵌套锁序恒为 `ticket → token`（`GetJsApiTicketAsync` 先拿 ticket 锁、锁内再 `await GetAccessTokenAsync`），无反向路径，故无死锁——这是应写进注释的不变式。
- `_accessToken` / `_tokenExpireTime` 未标 `volatile`，快路径理论上有边界竞态（最坏多刷一次），影响极小。
- token 失效重试在 `WeChatWorkServiceBase.ExecuteWithTokenRefreshAsync`：仅对 `42001/40014` 重试一次（先 `ForceRefreshAccessTokenAsync` 再重发）。

**进程内缓存**：`PmcBomService.cs` 用 `IMemoryCache` 缓存 BOM 工序结构（5 分钟），采用 `TryGetValue + Set` 非原子方式（未用 `GetOrCreateAsync`）。缓存的是只读快照，并发下最多重复查一次库，无正确性问题。

## 4. EF Core 乐观并发：RowVersion

**用到哪**：8 个实体声明 `[Timestamp] byte[] RowVersion`（`Domain/Pmc/PMC.cs`、`ExternalProduction*.cs`），如 `PMCDeliveryReview`、`WorkOrderSalesControl`、`ExternalProduction` 系列。`AppDbContext.OnModelCreating` 无额外 Fluent 配置，全靠 `[Timestamp]` 约定。

**逻辑**：每行带 SQL Server `rowversion` 版本戳。更新时 EF Core 生成的 SQL 形如 `UPDATE 表 SET ... WHERE 主键=@id AND RowVersion=@客户端版本`；若期间被别人改过，影响行数 0 → 抛 `DbUpdateConcurrencyException`。

**关键细节（disconnected 场景）**：服务端先 `FirstOrDefaultAsync` 加载实体时，`OriginalValue` 是刚读到的最新版本（等于没保护）。必须把**客户端上次读到的版本**覆盖回 `OriginalValue`，乐观并发才真正生效。封装在 `Application/Pmc/Services/PmcServiceBase.cs`：

```csharp
protected void ApplyClientRowVersion<TEntity>(TEntity trackedEntity, byte[]? clientRowVersion)
    where TEntity : class
{
    if (clientRowVersion is { Length: > 0 })
        _context.Entry(trackedEntity).Property("RowVersion").OriginalValue = clientRowVersion;
}
```

调用点共 8 处：`PmcWorkOrderService`（工单销控表含 `工单总数` 累加）、`PmcExternalProductionService`（发运/领料/生产/入库）、`PmcDeliveryReviewService`（外产订单/生产类型修改）。

**注意**：
- 客户端不传 `RowVersion` 时，退化为 **last-write-wins**——这是刻意的兼容性设计（老客户端无版本也能写），但意味着这些写没有并发保护。契约见 `docs/PMC-Concurrency-Deployment.md`：可变实体以 Base64 字符串暴露 `RowVersion`，客户端更新必须带上次读到的值，值过期返回 409 须 reload。
- 查询统一 `AsNoTracking()`（约 40 处），只有更新路径才走跟踪查询；`UserService` 甚至显式 `AsTracking()`。
- `SaveChanges` 全项目仅用 `await SaveChangesAsync()`，无同步调用。

## 5. 悲观并发与原子取号：sp_getapplock

**用到哪**：`Application/Pmc/Services/PmcBomService.cs` 的 `SaveExternalProductionBOM`。

**逻辑**：事务里有一段「读最大值 → +1 → 写回」的**非原子取号**，纯乐观并发挡不住（两个请求都读到旧 max，各自 +1 拿到同号）。因此在事务内显式加 SQL Server 应用锁，把这段串行化：

```csharp
var strategy = _context.Database.CreateExecutionStrategy();
return await strategy.ExecuteAsync(async () =>
{
    await using var transaction = await _context.Database.BeginTransactionAsync();
    await _context.Database.ExecuteSqlRawAsync(
        "DECLARE @lockResult int; " +
        "EXEC @lockResult = sp_getapplock @Resource = N'PMC:BOM:AtomicNumber', " +
        "@LockMode = 'Exclusive', @LockOwner = 'Transaction', @LockTimeout = 30000; " +
        "IF @lockResult < 0 RAISERROR(N'无法获得BOM原子取号锁,请稍后重试。', 16, 1);");

    var result = await SaveExternalProductionBOMCore(bomList, username, schedulingNo);
    await transaction.CommitAsync();
    return result;
});
```

`@LockOwner='Transaction'`：锁随事务提交/回滚自动释放。`@LockTimeout=30000`（30s）超时返回负值 → `RAISERROR` → 异常向上抛（由中间件兜底）。

**被该锁保护的取号逻辑**：
- `GenerateAnalysisOrderNumberAsync`：`PC{用户码}{yyMM}` 前缀求 max+1，补零 4 位。
- `SaveSchedulingAnalysisAsync`：`{userNum}UNT` 前缀求 max+1，补零 5 位。
- `ERPBaseService.GenerateCodeFromRecord`：对 `tb_control_id.currentcount` 纯内存自增（循环内不落库，靠该锁兜底）。

**注意**：本项目**未使用** SQL 锁提示（`UPDLOCK`/`TABLOCK`/`HOLDLOCK` 等）、未用 `MERGE`、upsert 全部在应用层「查存在 → 更新或新增」实现。

## 6. 事务与隔离级别

**默认隔离级别**：READ COMMITTED（代码从未显式指定 `IsolationLevel`，也无 `TransactionScope`）。意味着回退事务内「读→判断→写」存在理论写偏斜窗口，实际靠 rowversion / 唯一索引 / 应用锁在**写入时**兜底。

**显式事务（仅 2 处，且都配合 ExecutionStrategy）**：
1. `PmcBomService.SaveExternalProductionBOM`：事务 + `sp_getapplock` 原子取号（见 §5）。
2. `PmcDeliveryReviewService.ReturnDeliveryReview`：跨 8 张表的原子回退，事务内做状态机守卫（状态须「评审通过」、下游无实绩），并对 `ExecuteDeleteAsync` 做**受影响行数校验**补并发。

```csharp
var productionDeletedCount = await _context.外产_生产
    .Where(x => productionIds.Contains(x.编号)).ExecuteDeleteAsync();
if (productionDeletedCount != productionIds.Count)
    throw new ConflictException("外产生产数据删除不完整,退回操作已回滚,请重试");
```

**重试与事务的配合（关键点）**：因 `EnableRetryOnFailure(3, 2s)` 已开启，EF Core 会禁止裸用户事务（抛 `InvalidOperationException`），所以两处事务都必须包在 `CreateExecutionStrategy().ExecuteAsync(...)` 内。副作用：**整个委托可能被重放**，故委托内不能有不可重入的副作用（取号因在事务内 + 应用锁，回滚后重放安全）。

**隐式事务**：其余约 20 处写入依赖 EF Core 隐式事务——单次 `SaveChangesAsync` 内的多表变更自动成同一事务（如 `PmcDeliveryReviewService.cs:327` 注释「主记录与驳回原因回写处于同一事务」）。批量操作统一「内存改完 → 循环外一次 `SaveChangesAsync`」，减少锁持有时间。

## 7. 数据库护栏：唯一索引 / 唯一约束

**用到哪**：`Infrastructure/Data/AppDbContext.cs` Fluent 配置约 8 组唯一索引。

**逻辑**：把「业务键唯一」这个不变量**下沉到数据库**，作为「先查后插」竞态（TOCTOU）的最终兜底。并发下第二个请求撞已存在键，SQL Server 抛 `2601/2627`，应用层转 409。这是最便宜、最不可绕过的并发护栏。

```csharp
e.HasIndex(x => new { x.合同号, x.排产编号, x.货号 }).IsUnique();  // 生产类型修改 业务键
e.HasIndex(x => x.分析单号).IsUnique();                           // 排产分析单号
e.HasIndex(x => x.货号).IsUnique();                               // 工单销控货号
e.HasIndex(x => new { x.货号, x.分析单号 }).IsUnique();           // 工单销控明细
e.HasIndex(x => new { x.分析单号, x.货号 }).IsUnique();           // 外产_发运 / 外产_生产
e.HasIndex(x => x.UserName).IsUnique();                           // User
e.HasIndex(x => x.ChatId).IsUnique();                             // WechatWorkGroupChat
```

**配合 upsert**：应用层「`Any` 查存在 → `Add`/`Update`」式 upsert（如 `WeChatWorkGroupChatService`、`UserService` 注册查重），靠唯一索引兜底重复提交。典型幂等式 upsert（`PmcExternalProductionService.cs:45-84`）：按业务键查出已存在记录建字典，命中则 `ApplyClientRowVersion` + `SetValues` 更新，未命中则 `Add`，循环外一次性 `SaveChangesAsync`。

**上线脚本**：`DatabaseScripts/20260803_PMC_ConcurrencyAndIndexes.sql`
- 上线前先 `GROUP BY ... HAVING COUNT(*)>1` 校验业务键无重复，否则拒绝升级。
- 8 张表补 `rowversion` 列（DB-First 对接遗留 ERP 库，rowversion **不进 EF Migrations**，走手工脚本）。
- `SET XACT_ABORT ON` + `TRY/CATCH` 保证出错整事务回滚；含过滤唯一索引（兼容 SQL Server 2008 的 900 字节键长限制）。配套 `*.rollback.sql`。
- 部署顺序强约束：**先建 RowVersion 列再发 API**（`docs/PMC-Concurrency-Deployment.md`）。

## 8. 冲突的统一处理：409 收口

**用到哪**：`Api/Middlewares/GlobalExceptionMiddleware.cs`。

**逻辑**：不论乐观并发冲突还是唯一键冲突，统一映射为 **409 Conflict**，把冲突推给客户端（reload 再试），**服务端不做自动重试**。

```csharp
ConflictException or DbUpdateConcurrencyException => (StatusCodes.Status409Conflict, exception.Message),
DbUpdateException { InnerException: SqlException sqlException }
    when sqlException.Number is 2601 or 2627 =>
    (StatusCodes.Status409Conflict, "数据已被其他请求创建或修改,请刷新后重试。"),
```

**契约**（`docs/PMC-Concurrency-Deployment.md`）：可变实体暴露 `RowVersion` 为 Base64 字符串；客户端更新必须发送上次读到的值；值过期返回 409，客户端须 reload 后重试。

**其他映射**：`ValidationException/ArgumentException`→400；`NotFoundException`→404；`OperationCanceledException`（请求被取消）→499。

## 9. 异步与线程安全纪律

**`AppDbContext` 非线程安全**：禁止同一请求内并行 `await` 多个查询（无 `Task.WhenAll` 并发用同一 Context，否则抛 `InvalidOperationException`）。所有多次查询均顺序 `await`（如 `PmcSchedulingService` 连续 4 次批量查询）。

**无 sync-over-async**：全项目扫描 `.Result` / `.Wait()` / `.GetAwaiter().GetResult()` / `async void` 均为 **0 命中**，无线程池饥饿或经典死锁风险。异步互斥用 `SemaphoreSlim.WaitAsync` 而非同步 `Wait()`。

**CancellationToken 策略**：读路径普遍贯通 `CancellationToken`（控制器 → 服务 → 分页）；**写路径**（`SaveChangesAsync` / `CommitAsync` / Token 刷新）多数**不传 token**——有意为之的保守做法（避免提交中途被取消致状态不确定）。`OperationCanceledException` 映射 499。

无 `.ConfigureAwait(false)`：ASP.NET Core 无 SynchronizationContext，合理取舍。
