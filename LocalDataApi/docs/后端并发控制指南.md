# LocalDataApi 并发控制方案说明

> 本文用于说明 **`LocalDataApi` 当前已落地**的并发控制方法与逻辑，结合项目真实代码，便于团队 / 评审快速了解「我们用什么方式做并发控制」。
>
> 技术栈：.NET + EF Core（`AppDbContext`）+ SQL Server（对接遗留 ERP 库）。以下全部为已在代码中实际应用的能力。

---

## 1. 方案总览

本项目把并发控制做成由外到内的**四道防线**：

```
HTTP 请求
  │
  ├─ ① 入口限流   并发闸门 DatabaseHeavy
  │     同时放行 64，排队 256，超额返回 429
  │
  ├─ ② 单例资源保护   企业微信 Token 用 SemaphoreSlim 双检锁
  │     无锁快路径 + 锁内二次检查 + 提前失效
  │
  ├─ ③ 行级读写控制
  │     ├─ 乐观并发：实体带 RowVersion，更新带客户端版本 → 冲突 409
  │     └─ 悲观取号：事务内 sp_getapplock 串行化「读 max+1」
  │
  └─ ④ 数据库护栏   唯一索引 / 唯一约束 + rowversion 列
        所有并发写冲突经中间件统一收口为 409
```

核心策略：**用限流挡过载，用乐观并发 + 唯一索引兜大部分冲突，用悲观锁专门保护取号，用单例双检锁保护全局 token；冲突发生后统一返回 409 让客户端 reload，服务端不做自动重试。**

## 2. 入口限流：并发闸门 `DatabaseHeavy`

**作用**：在请求进入业务前限制同时进行的重数据库操作数，保护连接池不被打爆。

**用法**（`Program.cs`）：注册一个并发限流器，6 个 PMC 控制器统一标注 `[EnableRateLimiting("DatabaseHeavy")]`（如 `PMCBomController.cs:15`）。中间件顺序为 `UseRouting → GlobalExceptionMiddleware → UseRateLimiter → UseAuthorization`。

```csharp
var databaseConcurrency = builder.Configuration.GetValue("Performance:DatabaseConcurrency", 64);
var databaseQueue       = builder.Configuration.GetValue("Performance:DatabaseQueue", 256);
options.AddConcurrencyLimiter("DatabaseHeavy", limiter =>
{
    limiter.PermitLimit          = databaseConcurrency;  // 同时放行 64
    limiter.QueueLimit           = databaseQueue;        // 再多 256 排队
    limiter.QueueProcessingOrder = QueueProcessingOrder.OldestFirst;
});
// 拒绝时返回 429 + Retry-After: 1
```

**与连接池的配比**：`AddDbContextPool(poolSize: 256)` 提供 256 个复用连接，与限流的 64 并发 + 256 排队协调，避免「拿到线程却拿不到连接」空转。`AddDbContextPool` 语义仍是每请求一个 `AppDbContext` 实例（来自复用池）。

## 3. 单例资源保护：企业微信 Token 双检锁

**作用**：企业微信 `access_token` 是企业级全局配额（新 token 会让旧 token 失效），必须进程内共享一份缓存，不能每请求刷新。用异步双检锁保证并发下只刷新一次。

**用法**（`Infrastructure/WeChatWork/WechatWorkTokenProvider.cs`，注册为单例）：

```csharp
private readonly SemaphoreSlim _tokenLock  = new(1, 1);  // 保护 AccessToken 刷新
private readonly SemaphoreSlim _ticketLock = new(1, 1);  // 保护 JsApiTicket 刷新

public async Task<string> GetAccessTokenAsync(CancellationToken ct = default)
{
    if (_accessToken != null && _tokenExpireTime.HasValue
        && DateTimeOffset.UtcNow < _tokenExpireTime.Value)        // ① 无锁快路径（绝大多数请求命中）
        return _accessToken;

    await _tokenLock.WaitAsync(ct);                              // ② 进入异步互斥临界区
    try
    {
        if (_accessToken != null && _tokenExpireTime.HasValue
            && DateTimeOffset.UtcNow < _tokenExpireTime.Value)    // ③ 锁内二次检查，避免惊群重复刷新
            return _accessToken;

        var response = await _client.ExecuteCgibinGetTokenAsync(new CgibinGetTokenRequest(), ct);
        if (response.IsSuccessful())
        {
            _accessToken = response.AccessToken;
            _tokenExpireTime = DateTimeOffset.UtcNow
                .AddSeconds(response.ExpiresIn).AddMinutes(-5);   // ④ 提前 5 分钟失效，预留安全边界
            return _accessToken;
        }
        throw new InvalidOperationException($"获取 AccessToken 失败: [{response.ErrorCode}] {response.ErrorMessage}");
    }
    finally { _tokenLock.Release(); }                            // ⑤ 异常/取消路径都不死锁
}
```

**设计要点**：
- 用 `SemaphoreSlim` 而非 `lock`：临界区跨 `await`（HTTP 调用），`lock` 不允许 `await`。
- `try/finally + Release()`：保证异常与取消路径不泄漏许可。
- 提前 5 分钟失效：预留时钟偏移与网络抖动的安全边界。
- 内部只用 `IHttpClientFactory` 命名客户端，单例内不持有裸 `HttpClient`。
- 嵌套锁序恒为 `ticket → token`，无反向路径，因此无死锁。
- token 失效（`42001/40014`）由 `WeChatWorkServiceBase.ExecuteWithTokenRefreshAsync` 自动强制刷新并重试一次。

## 4. 乐观并发：实体 RowVersion

**作用**：防止两个请求基于同一旧版本修改同一行时后写覆盖先写（丢失更新）。

**用法**：8 个实体声明 `[Timestamp] byte[] RowVersion`（如 `PMCDeliveryReview`、`WorkOrderSalesControl`、`ExternalProduction` 系列），由 SQL Server 维护行版本。更新时 EF Core 生成 `UPDATE ... WHERE 主键=@id AND RowVersion=@客户端版本`，版本不匹配则抛 `DbUpdateConcurrencyException`。

由于本项目是 disconnected 场景（先查出实体再改），必须把**客户端上次读到的版本**覆盖回 `OriginalValue` 才生效，封装在 `Application/Pmc/Services/PmcServiceBase.cs`：

```csharp
protected void ApplyClientRowVersion<TEntity>(TEntity trackedEntity, byte[]? clientRowVersion)
    where TEntity : class
{
    if (clientRowVersion is { Length: > 0 })
        _context.Entry(trackedEntity).Property("RowVersion").OriginalValue = clientRowVersion;
}
```

调用点共 8 处：`PmcWorkOrderService`（工单销控表含 `工单总数` 累加）、`PmcExternalProductionService`（发运/领料/生产/入库）、`PmcDeliveryReviewService`（外产订单/生产类型修改）。

**用法约定**：查询统一 `AsNoTracking()`（约 40 处），只有更新路径才走跟踪查询；`SaveChanges` 全项目仅用 `await SaveChangesAsync()`。可变实体以 Base64 字符串向前端暴露 `RowVersion`，前端更新时带上次读到的值，值过期返回 409 须 reload。

## 5. 悲观并发与原子取号：sp_getapplock

**作用**：事务里「读最大值 → +1 → 写回」的取号逻辑是非原子的，乐观并发挡不住（两个请求都读到旧 max 会拿到同号）。用 SQL Server 应用锁在事务内把这段串行化。

**用法**（`Application/Pmc/Services/PmcBomService.cs` 的 `SaveExternalProductionBOM`）：

```csharp
var strategy = _context.Database.CreateExecutionStrategy();
return await strategy.ExecuteAsync(async () =>
{
    await using var transaction = await _context.Database.BeginTransactionAsync();
    await _context.Database.ExecuteSqlRawAsync(
        "DECLARE @lockResult int; " +
        "EXEC @lockResult = sp_getapplock @Resource = N'PMC:BOM:AtomicNumber', " +
        "@LockMode = 'Exclusive', @LockOwner = 'Transaction', @LockTimeout = 30000; " +
        "IF @lockResult < 0 RAISERROR(N'无法获得BOM原子取号锁,请稍后重试。', 16, 1);");

    var result = await SaveExternalProductionBOMCore(bomList, username, schedulingNo);
    await transaction.CommitAsync();
    return result;
});
```

`@LockOwner='Transaction'`：锁随事务提交/回滚自动释放；`@LockTimeout=30000`（30s）超时返回负值并转异常。被该锁保护的取号逻辑：`GenerateAnalysisOrderNumberAsync`（`PC{用户码}{yyMM}` 前缀 max+1）、`SaveSchedulingAnalysisAsync`（`{userNum}UNT` 前缀 max+1）、以及 `ERPBaseService.GenerateCodeFromRecord` 对 `tb_control_id.currentcount` 的内存自增。

## 6. 事务与隔离级别

**作用**：保证多表写操作的原子性，以及重试与事务的正确配合。

**用法**：
- 默认隔离级别 READ COMMITTED（未显式指定，依赖 SQL Server 默认）。
- **2 处显式事务**，均包在 `CreateExecutionStrategy().ExecuteAsync(...)` 内以配合 `EnableRetryOnFailure(3, 2s)`：
  1. `PmcBomService.SaveExternalProductionBOM`：取号事务 + `sp_getapplock`。
  2. `PmcDeliveryReviewService.ReturnDeliveryReview`：跨 8 张表的原子回退，事务内做状态机守卫（状态须「评审通过」、下游无实绩），并对 `ExecuteDeleteAsync` 做受影响行数校验补并发。
- **隐式事务**：其余约 20 处写入依赖 EF Core 隐式事务——单次 `SaveChangesAsync` 内的多表变更自动成同一事务；批量操作统一「内存改完 → 循环外一次 `SaveChangesAsync`」，减少锁持有时间。

## 7. 数据库护栏：唯一索引 / 唯一约束

**作用**：把「业务键唯一」这个不变量下沉到数据库，作为「先查后插」竞态的最终兜底（撞重复键转 409）。

**用法**（`Infrastructure/Data/AppDbContext.cs` 配置约 8 组唯一索引）：

```csharp
e.HasIndex(x => new { x.合同号, x.排产编号, x.货号 }).IsUnique();  // 生产类型修改 业务键
e.HasIndex(x => x.分析单号).IsUnique();                           // 排产分析单号
e.HasIndex(x => x.货号).IsUnique();                               // 工单销控货号
e.HasIndex(x => new { x.货号, x.分析单号 }).IsUnique();           // 工单销控明细
e.HasIndex(x => new { x.分析单号, x.货号 }).IsUnique();           // 外产_发运 / 外产_生产
e.HasIndex(x => x.UserName).IsUnique();                           // User
e.HasIndex(x => x.ChatId).IsUnique();                             // WechatWorkGroupChat
```

应用层采用「`Any` 查存在 → `Add`/`Update`」式 upsert（如 `WeChatWorkGroupChatService`、`UserService` 注册查重），由唯一索引兜底重复提交。典型幂等式 upsert（`PmcExternalProductionService.cs`）：按业务键查出已存在记录建字典，命中则 `ApplyClientRowVersion` + `SetValues` 更新，未命中则 `Add`，循环外一次性 `SaveChangesAsync`。

配套上线脚本 `DatabaseScripts/20260803_PMC_ConcurrencyAndIndexes.sql`：上线前校验业务键无重复；8 张表补 `rowversion` 列（DB-First 对接遗留库，rowversion 走手工脚本而非 EF Migrations）；`SET XACT_ABORT ON` + `TRY/CATCH` 保证出错整事务回滚；含过滤唯一索引（兼容 SQL Server 2008 的 900 字节键长限制）。部署顺序强约束：先建 RowVersion 列再发 API。

## 8. 冲突统一收口：409

**作用**：不论乐观并发冲突还是唯一键冲突，统一返回 409 让客户端 reload 重试，服务端不自动重试。

**用法**（`Api/Middlewares/GlobalExceptionMiddleware.cs`）：

```csharp
ConflictException or DbUpdateConcurrencyException => (StatusCodes.Status409Conflict, exception.Message),
DbUpdateException { InnerException: SqlException sqlException }
    when sqlException.Number is 2601 or 2627 =>
    (StatusCodes.Status409Conflict, "数据已被其他请求创建或修改,请刷新后重试。"),
```

契约（`docs/PMC-Concurrency-Deployment.md`）：可变实体暴露 `RowVersion` 为 Base64 字符串，客户端更新必须发送上次读到的值，值过期返回 409 须 reload。其他映射：`ValidationException/ArgumentException`→400、`NotFoundException`→404、请求取消 `OperationCanceledException`→499。

## 9. 异步与线程安全纪律

**作用**：从编码层面避免线程安全问题。

**用法**：
- `AppDbContext` 非线程安全，项目中所有多次查询均顺序 `await`（如 `PmcSchedulingService` 连续 4 次批量查询），不并行复用同一 Context。
- 全项目无 sync-over-async（`.Result` / `.Wait()` / `.GetAwaiter().GetResult()` / `async void` 均为 0 命中），无线程池饥饿或死锁风险；异步互斥用 `SemaphoreSlim.WaitAsync`。
- `CancellationToken` 在读路径贯通（控制器 → 服务 → 分页），写路径刻意不传以避免提交中途取消导致状态不确定；请求取消映射为 499。
